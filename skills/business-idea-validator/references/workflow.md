## 1. Choose the mode and depth

### Evaluate

Use for one explicit business or product idea. Run all seven decision gates. Research only the facts needed to distinguish `PURSUE`, `TEST`, `PIVOT`, `PARK`, and `DROP`.

### Compare

Use for two to five supplied ideas.

1. Normalize every idea using the same fields.
2. Run a lightweight gate screen for all ideas.
3. Identify fatal flaws before scoring relative strengths.
4. Deepen only the leading one or two ideas.
5. Return one comparison table and one compact recommendation, not several full reports.

### Explore

Use when the user supplies a problem, market, customer group, capability, asset, or founder constraint but no clear idea.

1. Translate the supplied context into opportunity constraints.
2. Generate at most four materially different candidates by default; use up to six only when the user explicitly requests broad exploration.
3. Ensure candidates differ in buyer, trigger, workflow, or delivery model—not merely features.
4. Run a lightweight screen.
5. Deepen the best one or two.
6. Permit the conclusion that no candidate is strong enough.

### Update

Use after new interviews, payments, objections, usage, competitor changes, legal findings, or product tests.

1. Preserve the previous opportunity framing unless the evidence disproves it.
2. Identify which claims and gates the new evidence affects.
3. Show gate changes as `previous → current`.
4. Revise the verdict, confidence, pivots, and next test only where justified.
5. Avoid repeating unchanged research.

### Research depth

- Use **triage** for preliminary reasoning or when browsing is unavailable or prohibited.
- Use **standard** for the normal decision card.
- Use **deep** only when requested or when legal, capital, liability, integration, or market-structure uncertainty could reverse the verdict.

## 2. Normalize the input

Extract these fields when present:

| Field | Meaning |
| --- | --- |
| Decision | What the user needs to decide now |
| Idea | Product, service, workflow, or business model being considered |
| Buyer | Role or organization controlling budget |
| User | Person performing or receiving the workflow |
| Trigger | Event that makes the problem timely |
| Current method | Software, labor, service, workaround, avoidance, or doing nothing |
| Consequence | Cost, risk, delay, lost revenue, anxiety, or liability |
| Outcome | Result the buyer would pay to obtain |
| Frequency | How often the trigger and workflow recur |
| Founder context | Build, domain, trust, capital, and lifestyle constraints |
| Known evidence | Payments, interviews, complaints, workflows, pricing, links, or experiments |
| Constraints | Geography, time, budget, regulation, support, service, integrations, or exclusions |

Do not invent missing values. Mark consequential unknowns for research or validation.

## 3. Frame the opportunity

Create one sentence:

> When **[trigger]** occurs, **[specific buyer]** currently **[workaround]**, which causes **[measurable cost, risk, delay, or lost revenue]**. The proposed offer delivers **[specific outcome]**.

If the sentence remains vague, the idea is not ready for a positive verdict. Narrow the buyer, trigger, workflow, or outcome before expanding features.

Identify no more than three consequential assumptions. Prefer assumptions that could reverse the verdict, such as buyer urgency, willingness to pay, workflow clarity, legal permission, access to data, or recurring behavior.

## 4. Route the investigation

Always use these profiles:

1. Demand and workflow
2. Competition and wedge
3. Operator and economics
4. Durability and red team

Use a specialist profile only when a material risk or opportunity requires it. Do not run every specialist profile by default.

Assign each profile distinct questions. Require each profile to return structured claims for the evidence ledger, not a standalone essay.

## 5. Research by decision value

Prioritize unknowns that can change the verdict. Use this order:

1. Does a specific buyer experience a costly or urgent consequence?
2. Is there evidence of existing spend, budget, or costly behavior?
3. Are the buyer, user, budget owner, and workflow specific enough to form a testable offer?
4. Does a credible wedge remain against all substitutes?
5. Can the economics support delivery, onboarding, and support?
6. Are legal, technical, security, operational, or capital requirements acceptable?
7. Does value survive cheaper technology and incumbent response?

Use research stopping rules:

- Stop competitor discovery after 3–7 representative alternatives cover direct products, adjacent products, services, generic tools, DIY, and status quo.
- Stop collecting sources for a claim after strong sources converge and additional evidence is unlikely to change its gate.
- Stop a branch early when a fatal flaw is well supported.
- Mark a claim `UNKNOWN` when evidence remains unavailable; do not fill the gap with narrative.
- Deepen contradictory evidence before deepening already-settled claims.

## 6. Merge evidence and contradictions

Create an internal ledger with these fields:

| Field | Required content |
| --- | --- |
| Claim | One decision-relevant proposition |
| State | `fact`, `inference`, `assumption`, or `unknown` |
| Source and date | Best support available |
| Direction | `supports`, `contradicts`, or `context` |
| Gate | Which decision gate it affects |
| Confidence | `low`, `medium`, or `high` |
| Implication | How it changes the idea, pivot, verdict, or test |

Merge duplicate claims. Preserve contradictory claims rather than averaging them into ambiguity. Explain the contradiction and identify the cheapest evidence that could resolve it.

## 7. Design repair pivots

Create a pivot only when it repairs a `WEAK` or `UNKNOWN` gate.

Allowed variables:

- Buyer
- User
- Trigger
- Workflow owned
- Outcome
- Scope
- Delivery model
- Pricing unit
- Responsibility or risk assumed

Change no more than two variables per pivot. Keep enough of the original insight to make the comparison useful.

Useful pivot patterns:

- Narrow to the most urgent trigger.
- Sell a smaller, measurable outcome.
- Replace software-first with a paid concierge or productized service.
- Sell to a repeat or portfolio buyer when end-user demand is episodic.
- Sell a supporting workflow to an incumbent rather than displacing it.
- Remove a regulated, capital-intensive, or unreliable step.
- Shift from information to execution when customers pay for completion.
- Shift from execution to workflow support when liability makes outcome ownership unattractive.

Reject cosmetic pivots such as adding AI, changing branding, adding a dashboard, or moving to a different industry without repairing a gate.

## 8. Judge and synthesize

1. Assign every gate a signal and concise rationale.
2. Identify any fatal flaw.
3. Classify market crowding.
4. Select the best current version and strongest repair pivot.
5. Choose a verdict and confidence.
6. Design a test for the highest-impact unknown.
7. Compose only the final integrated answer.

Do not reveal internal profile transcripts or hidden reasoning. Surface evidence, assumptions, contradictions, and decision logic in concise form.

## 9. Update after real evidence

When the user returns with test results:

1. Convert each result into an evidence state.
2. Distinguish qualified participants from friends, peers, or people outside the target workflow.
3. Distinguish stated interest from meaningful commitment.
4. Update the affected gate signal and confidence.
5. Check whether the strongest pivot changed.
6. Design the next test only if a material uncertainty remains.

Repeatedly failing the same meaningful commitment test should lower the verdict rather than trigger endless copy or feature changes.
